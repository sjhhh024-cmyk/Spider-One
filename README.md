# 爬虫员工平台愿景与待办

## 一句话定位

这是一个面向真实业务任务的“AI 爬虫员工”平台。它不是单一站点的脚本，也不是只能写固定字段的采集器，而是一套可以接收自然语言任务、自动判断采集路线、组织执行、校验结果、沉淀经验的运行体系。

## 我们为什么要做这件事

传统爬虫项目通常有几个问题：

- 站点一变就要重写
- 字段一变就要改代码
- 新项目一多，目录和脚本很快失控
- 任务跑挂后很难恢复
- 代码只适合作者自己看，不适合团队维护
- 动态页面、接口重放、翻页、检索、JS 逆向经常是分散处理，缺少统一方法

我们要解决的不是“再写一个爬虫”，而是“做一个能长期干活、能交接、能扩展的爬虫员工体系”。

## 项目愿景

### 近期愿景

先做出一套真正可运行的基础平台，让它能够：

- 接收自然语言形式的采集任务
- 将任务拆分成可执行的子任务
- 支持接口采集、页面解析、浏览器侦察
- 支持分页、检索、顺序采集、失败重试
- 将最终业务数据干净地写入 MySQL
- 在项目级别支持断点续跑和失败恢复

### 中期愿景

把它从“能跑”提升到“稳定可复用”，让它能够：

- 支持多项目并行
- 支持多站点规则沉淀
- 支持项目包独立运行
- 支持统一验证、导出、日志与告警
- 支持将经验沉淀成 skill、规则和模板

### 长期愿景

把它建设成一个真正的 AI 数字员工平台，让它能够：

- 像人一样接任务、拆任务、汇报进度
- 像系统一样调度 worker、恢复失败、保证稳定
- 像团队资产一样可维护、可交接、可持续积累

## 核心设计原则

- 平台和项目解耦：平台负责共性能力，项目负责站点个性能力。
- MySQL 只放最终业务数据，不承担任务调度状态。
- Redis 负责运行时调度，SQLite 负责项目级任务账本。
- 项目包必须可以脱离平台独立运行。
- 目录必须清晰规整，代码必须可读、可改、可扩展。
- 遵守 Python 官方风格，优先人类可维护性。

## 最终想做成什么样

理想状态下，这个平台会由三部分组成：

1. `Skill`
负责理解自然语言任务、判断技术路线、指导执行。

2. `Runtime`
负责统一调度、重试、限流、验证、导出、日志和执行器协作。

3. `Project Package`
负责每个项目自己的站点配置、采集器、解析器、状态账本和输出目录。

整体工作方式是：

`用户下任务 -> Skill 理解并拆解 -> Runtime 调度 -> Worker 执行 -> 项目包产出结果 -> MySQL 落最终数据`

## 当前已经明确的技术路线

- 语言：`Python 3.12`
- 请求采集：`httpx`
- 浏览器自动化：`Playwright`
- 稳定规则型抓取：`Scrapy`
- 调度层：`Redis`
- 项目级任务账本：`SQLite`
- 最终业务数据：`MySQL`
- 测试：`pytest`
- 代码质量：`ruff`

## 当前阶段要做的事情

### 第一阶段：打基础

- 完成 `runtime` 基础骨架
- 定义任务模型与状态机
- 完成 SQLite 任务账本
- 建立最小测试体系

### 第二阶段：让任务流起来

- 完成 Redis 队列适配
- 完成 dispatcher 和 scheduler
- 定义统一 worker 协议
- 先接入 `http worker`
- 再接入 `browser worker`

### 第三阶段：让结果能交付

- 完成 validator
- 完成 JSONL / CSV exporter
- 完成 MySQL 最终结果写入
- 明确业务表结构和去重策略

### 第四阶段：让项目能独立运行

- 建立标准项目目录结构
- 建立示例项目包
- 支持 `run / validate / export`
- 保证项目脱离平台仍能跑

### 第五阶段：增强复杂场景能力

- 接入 `scrapy worker`
- 接入 `reverse worker`
- 完善站点 profile 和规则沉淀
- 增加监控、日志分类、告警

## 当前阶段不做的事情

为了控制复杂度，首版明确不追求这些：

- 一开始就做超重的微服务化
- 一开始就做 Kafka、分库分表、大数据平台
- 一开始就支持所有类型网站
- 一开始就把所有执行器全部做完
- 一开始就做花哨的管理界面

首版重点只有一句话：

`先把任务流、状态流、数据流跑顺。`

## 对代码和目录的要求

这不是一个只给 AI 看懂的项目，也不是一个只给当前作者自己维护的项目。后续所有实现都必须满足：

- 文件职责明确
- 模块边界清晰
- 目录规整
- 命名直观
- 避免大而杂的工具文件
- collector、parser、pipeline、validator、exporter 分层明确
- 测试优先，先红后绿

## 成功标准

当下面这些事情能够稳定做到时，说明这套平台开始真正有价值：

- 给一句自然语言任务，系统能拆成可执行任务
- 新项目可以快速按标准结构创建
- 任务中断后可以恢复
- 最终数据可以干净进入 MySQL
- 项目可以独立运行，不依赖整个平台才能工作
- 代码别人能看懂、能接手、能继续改

## 当前结论

这个项目的目标不是“写几个爬虫脚本”，而是“建设一个可以长期演进的 AI 爬虫员工平台”。  
它的核心竞争力不是某个站点爬得快，而是：

- 接任务的能力
- 选择路线的能力
- 组织执行的能力
- 失败恢复的能力
- 沉淀经验的能力

后续所有开发、重构和新增功能，都应该围绕这个方向展开，而不是回到“一站一脚本”的老路上。
