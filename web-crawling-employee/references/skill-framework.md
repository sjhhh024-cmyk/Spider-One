# Skill Framework

## 定位

这个 skill 不是“一个爬虫脚本模板”，也不是“某个医生站点的专用采集器”。

它的定位是：网站采集员工的任务大脑。  
负责把用户的自然语言任务，转换成一套可执行、可验证、可交付、可复用的网站采集工作流。

医生信息站点是当前重点场景，但这个 skill 的骨架必须对医院、机构、科室、文章、商品、企业名录等其他实体保持通用。

## 一句话理解

`Skill 决定怎么干，Runtime 负责把活跑起来，Project Package 负责把具体站点的活干细。`

## 你可以把它理解成一个六岗小组

| 角色 | 负责什么 | 产出什么 |
|---|---|---|
| 接单员 | 听懂用户要什么数据、范围多大、何时算完成 | 任务单 |
| 侦察员 | 看页面、看接口、看搜索、看翻页、看详情关系 | 站点地图 |
| 路线师 | 判断走接口、HTML、浏览器还是逆向 | 路线方案 |
| 调度员 | 把任务拆成列表、详情、检索、顺序、重试等动作 | 执行清单 |
| 质检员 | 判断结果是否可信、是否漏页、是否重复、是否字段为空 | 验收报告 |
| 档案员 | 把字段经验、站点经验、失败样例、复现方法沉淀下来 | 知识资产 |

这六个角色不一定对应六份代码，而是 skill 的六类核心能力。

## 总体工作链路

```text
用户一句话下任务
  -> 接单澄清
  -> 站点侦察
  -> 路线决策
  -> 执行编排
  -> 结果验证
  -> 交付与沉淀
```

## 六层结构

### 1. 任务理解层

把自然语言要求转成内部任务单，至少明确：

- 目标站点
- 目标实体
- 用户指定字段
- 采集范围
- 停止规则
- 交付形式
- 风险和阻塞项

这一层的目标不是先写代码，而是先把“到底要干什么”定清楚。

### 2. 站点侦察层

识别网站的真实结构和数据入口：

- 列表页、详情页、搜索页、筛选页
- 分页方式
- 页面内嵌数据
- 网络接口
- 是否存在签名、加密、动态令牌

这一层产出的不是结果数据，而是“站点地图”和“候选路线”。

### 3. 路线决策层

按成本和稳定性从低到高选择：

1. 已观察到的 JSON / GraphQL 接口
2. 页面内嵌 JSON
3. 稳定 HTML 解析
4. 浏览器侦察后请求重放
5. 浏览器直接提取
6. 最小必要 JS 逆向

skill 的核心价值之一，就是不要一上来就把任务打成重型浏览器自动化或整站逆向。

### 4. 执行编排层

把路线变成可执行动作，常见动作包括：

- 列表采集
- 详情扩展
- 检索采集
- 翻页推进
- 顺序采集
- 失败重试
- 样本验证

如果接入 runtime，这一层会转给 dispatcher、scheduler 和 worker。  
如果没有 runtime，这一层也要能指导单项目脚本独立完成任务。

### 5. 验收交付层

交付前必须验证：

- 采到的是否真是目标实体
- 用户要求字段是否存在
- 关键字段是否为空
- 翻页是否真的推进
- 检索参数是否真的生效
- 列表和详情是否正确合并
- 是否保留来源和追踪信息

这一层决定“能不能交付”，而不是“代码有没有跑完”。

### 6. 经验沉淀层

每做完一次任务，都要尽量沉淀：

- 字段映射经验
- 分页规则
- 搜索参数规律
- 去重键
- 常见失败点
- 复现方式

这层决定这个 skill 是一次性助手，还是会越做越强的数字员工。

## Skill 的输入和输出

### 输入

- 用户自然语言任务
- 用户给出的站点链接或站点名称
- 用户指定的数据字段和范围
- 用户对样本、全量、代码、导出格式的要求

### 输出

- 内部采集任务单
- 站点侦察结论
- 技术路线选择
- 执行步骤或项目实现方案
- 验收结论
- 结果数据或可复现交付物

## Skill 的边界

skill 负责“理解、判断、指导、验收”，但不应该被误解成下面这些东西：

- 不是固定字段模板
- 不是只服务医生信息
- 不是长期状态存储层
- 不是某个具体站点脚本
- 不是默认绕过登录、验证码、付费或强校验页面的工具

## Skill 与 Runtime 的关系

二者关系应该固定成下面这样：

- `Skill`：大脑，决定做什么、怎么做、做到什么程度算完成
- `Runtime`：中控，负责调度、重试、限流、恢复、导出
- `Project Package`：项目班组，负责具体站点逻辑和独立运行
- `Redis`：执行窗口和短期调度
- `SQLite`：项目账本和断点恢复
- `MongoDB`：最终业务结果

也就是说，skill 是上层总指挥，不是下层存储或执行器本身。

## Skill 包内文件分工

- `SKILL.md`：总入口，告诉代理应该怎么接任务、怎么思考、先看哪些规则
- `references/skill-framework.md`：大框架，定义 skill 的角色、分层和边界
- `references/task-playbook.md`：技术树和侦察打法
- `references/field-strategy.md`：动态字段策略
- `references/test-checklist.md`：验收标准
- `references/runtime-architecture.md`：当任务进入长期运行或平台化阶段时，再看这份运行时架构
- `scripts/validate_records.py`：机器校验工具

## 单项目落地原则

当任务还是单站点、单接口、单项目阶段时，优先让项目“人一眼能看懂”：

- 配置直接放 `profile.yml`
- 主脚本直接放顶层，命名按 `{entity}_{source}_start.py`
- 环境准备单独放 `start.ps1`

例如：

- `doctor_hxq_start.py`
- `article_xxx_start.py`

不要为了“像框架”而过早把简单项目拆成很多层。  
先让入口明显、配置明显、核心文件明显，再考虑是否升级成 `src/` 包结构。

同时要保证代码说明足够直接：

- 每个函数都要有简短注释或文档字符串
- 如果使用类，每个类也要有简短说明
- 注释要说明“这个函数/类负责什么”，不要只重复代码字面意思

代码风格默认优先向“人类工程师顺手写出来的单机脚本”靠拢：

- 主流程最好能一眼看出是：读配置 -> 发请求 -> 解析列表 -> 整理字段 -> 写库
- 能用少量函数讲清楚，就不要拆出很多 service、manager、pipeline
- 如果要用类，优先一个简单 spider 类，把请求、解析、入库收在一起
- 函数名和字段名要贴近业务，不要过度抽象
- 读代码的人应该很快定位到“入口在哪、请求在哪、解析在哪、入库在哪”
- MongoDB 默认优先使用业务唯一键作为 `_id`，不要无意义地交给 MongoDB 自动生成 ObjectId
- 写法上宁可朴素直接，也不要为了形式上的“高级感”牺牲可读性

如果是 Scrapy 项目，也沿用同样的可读性原则，但组织形式遵守 Scrapy 原生习惯：

- 保留 `scrapy.cfg`、项目包、`settings.py`、`pipelines.py`、`middlewares.py`、`spiders/`
- spider 可以按阶段拆分，例如“列表 -> 明细 URL -> 明细页”，文件名允许直接体现阶段顺序
- 优先给一个明显的总入口，例如很薄的 `start.py`、`start.ps1` 或自定义 command
- `settings.py`、`pipelines.py`、spider 本身都优先写得直白，不要再套很多额外抽象层
- Scrapy 项目也要让人很快定位到“入口在哪、settings 在哪、pipeline 在哪、spider 在哪”

如果是分阶段 Scrapy 项目，再补几条落地规则：

- 如果第一阶段是自己起始请求、不是从 Redis 消费种子，就优先用普通 `scrapy.Spider`，不要为了形式统一强行继承 `RedisSpider`
- 只有真正需要从 Redis 取起始任务的阶段，才使用 `RedisSpider`
- 使用 `RedisSpider` 的阶段要明确空闲关闭策略，例如设置 `MAX_IDLE_TIME_BEFORE_CLOSE` 和 `SCHEDULER_IDLE_BEFORE_CLOSE`
- 单入口串行启动多个阶段时，要验证“上一阶段能退出、下一阶段能继续”，不要出现采完了但进程一直空转不结束
- 如果 Redis 依赖 SSH 隧道，优先在总入口里先做隧道准备或 Redis 连通性预检，再启动 Scrapy
- Windows 环境下，`scrapy.cfg` 尽量保持纯 ASCII，避免因为编码问题在读取项目配置时直接报错

同时要保证运行时可观察：

- 默认把关键过程日志直接打印到控制台
- 至少打印当前页码、请求地址、响应条数、去重后条数
- 入库前要打印本次实际入库的字段名
- 至少打印一条样本记录的字段值，而且要按行展示，方便人直接核对
- 入库成功数、失败数和异常原因也要打印出来

不要做成“代码跑完了，但控制台几乎没信息，只能去数据库里猜发生了什么”。

如果项目进入 Scrapy 或分布式阶段，就按对应框架的原生结构组织，不强行套单机脚本命名规则。

## 扩展原则

- 新站点增加时，优先补侦察经验和项目包，不推翻 skill 主骨架。
- 新字段增加时，优先放进任务字段和扩展字段，不把 schema 写死。
- 新执行器增加时，扩 runtime 和项目实现，不改变 skill 的核心判断顺序。
- 任务量增加时，优先扩调度和分片能力，不改变 skill 的接单和验收逻辑。

## 当前先不定死的东西

当前只定大框架，不提前锁死下面这些细节：

- 具体 MongoDB collection 设计
- 具体任务表字段
- 代理池产品方案
- 每个网站的独立字段全集
- 复杂反爬场景的逐站对抗细节

先把骨架定清楚，再按项目逐步长肉。
